## 문제: 결제 상태를 누가 책임질 것인가

토글 1.0(외주 PHP 기반 레거시)은 프론트가 PortOne 결제를 완료한 직후, 직접 서버에 "결제완료"라고 상태를 업데이트하는 구조였습니다. 문제는 결제는 실제로 끝났는데 그 직후 클라이언트 통신이 끊기면, 서버는 영영 그 사실을 모른다는 점이었습니다. 결제 상태의 진실이 클라이언트의 네트워크 상태에 달려 있었던 셈입니다.

토글 3.0을 리빌드하면서 결제·취소·인증·알림 영역을 맡아, 이 정합성 문제를 근본적으로 다시 설계해야 했습니다.

## Webhook을 유일한 상태 변경 주체로

PortOne API 문서를 검토한 뒤, 서버가 결제 상태의 단일 진실 공급원(source of truth)이 되도록 구조를 바꿨습니다.

- 프론트는 PortOne SDK로 결제를 진행하고, 완료 후 백엔드에 "확인해달라"는 신호만 보냅니다.
- 실제 상태를 바꾸는 건 오직 **PortOne Webhook**뿐입니다. 프론트의 호출은 상태를 조회(GET)할 뿐, 직접 쓰지 않습니다.
- 상태 전이는 `prepared → completed`로만 가능하도록 가드를 걸었습니다. 같은 Webhook이 재전송되더라도 이미 `completed`면 그대로 무시해, 멱등한 상태 전이를 보장했습니다.

이 구조 덕분에 클라이언트 통신 장애로 인한 정합성 이슈는 완전히 사라졌습니다.

## Stripe에서는 idempotency key로 요청 자체를 멱등하게

같은 시기 진행한 오픈플랜 Global MVP(싱가포르 대상 해외여행자보험)에서는 Stripe를 연동했는데, 여기서는 결제 "요청" 자체의 중복을 막는 문제를 다뤘습니다.

네트워크 재시도 등으로 동일한 결제 요청이 두 번 전송될 수 있는데, Stripe PaymentIntent 생성 시 **백엔드가 자체 생성한 결제(주문) 번호를 idempotency key로 전달**하도록 했습니다. 같은 key로 재시도 요청이 들어와도 Stripe는 새 결제를 만들지 않고 기존 처리 결과를 그대로 반환합니다.

전체 흐름은 이렇습니다: 프론트가 결제 요청 → 백엔드가 Stripe 모듈로 결제 URL을 생성해 전달 → 사용자가 결제 진행 → Stripe Webhook이 백엔드의 결제 상태를 갱신 → 프론트는 몇 초 뒤 상태 확인 API를 폴링해 화면에 반영. PG사와 국가는 다르지만, "Webhook만 상태를 쓰고 프론트는 조회만 한다"는 원칙은 PortOne 케이스와 동일하게 적용했습니다.

## 환불에도 같은 원칙을 재사용

환불도 Stripe가 제공하는 환불 API를 연동했고, 환불 완료 여부 역시 Webhook으로 상태를 갱신했습니다. 환불 "요청" 자체의 중복 호출은 결제 때와 같은 상태 가드 패턴으로 막았습니다 — 이미 `refund_requested`나 `refunded` 상태면 Stripe 환불 API를 다시 호출하지 않습니다. 하나의 설계 원칙을 결제와 환불에 일관되게 적용한 셈입니다.

## 한계와 다음 단계

지금 돌이켜보면 상태 전이 체크(`if status == prepared`)는 애플리케이션 레벨에서만 이뤄졌습니다. PortOne처럼 Webhook을 재시도 전송하는 PG의 경우, 이론적으로는 거의 동시에 두 요청이 들어오면 체크와 업데이트 사이의 좁은 시간 창에서 중복 처리가 발생할 여지가 있습니다. 다시 설계한다면 JPA `@Version` 기반 낙관적 락이나 DB 레벨 락을 추가해 동시성까지 확실히 보장하고 싶습니다.

외부 시스템의 비동기 이벤트를 신뢰성 있게 받아 상태를 관리하는 이 패턴은, PG사나 도메인이 바뀌어도(심지어 결제가 아닌 다른 비동기 처리 결과를 다루는 상황이어도) 그대로 재사용할 수 있는 설계 원칙이라고 생각합니다.
